# Мост Tasker между экземплярами Cronopus

Дата: 2026-10-15. Статус: согласована пользователем; подготовка плана реализации.

## 1. Цель и согласованные требования

Локальный Cronopus управляет Tasker серверного Cronopus по публичному IP.
У сервера нет домена, VPN или HTTPS-прокси; сейчас доступ осуществляется через RDP.
Мост должен позволять готовить и запускать задачи без постоянного использования RDP.

- В Tasker выбирается один узел: «Локальный» или сохранённое подключение.
- Нужны создание, клонирование, редактирование и удаление задач, настройки и payload.
- Нужны расписания, включение/выключение, пауза, отсрочка, очередь, запуск и остановка.
- Скрипты выбираются на сервере; локальные файлы и папки можно загружать на сервер.
- Доступны все диски и каталоги в пределах прав процесса серверного Cronopus.
- Последний открытый каталог запоминается отдельно для каждого подключения.
- Логи загружаются ограниченными порциями по запросу; наблюдение включается отдельно.
- Предусматривается работа сервера с тысячей одновременно выполняющихся экземпляров.
- Прямой HTTPS, сертификат сервера с проверкой отпечатка и отдельные ключи доступа.

Следующие разделы конкретизируют согласованную архитектуру. Численные лимиты и
детали протокола являются предложенными решениями для проверки этой спецификации.

## 2. Основа в текущем репозитории

`Controllers/EmbeddedServer.cs` обслуживает локальную панель через HttpListener.
Основной порт по умолчанию — 33333; replay использует фактический порт панели + 1.
Этот сервер остаётся локальным: он также предоставляет терминал и конфигурацию.
`Handlers/SchedulerHandler.cs` содержит HTTP-команды Tasker и локальные действия.
`Controllers/SchedulerService.cs` и `.Control.cs` выполняют задачи и управляют состоянием.
`Handlers/TaskControlHandler.cs` и `TasksControlHandler.cs` используют токены запусков.
Эти токены сохраняют своё назначение и не дают доступ к новому удалённому входу.
`wwwroot/js/tasker.js` сейчас обращается к локальным маршрутам напрямую и включает SSE.
`Program.cs` создаёт единственный планировщик и регистрирует обработчики.
Проект собирается для `net10.0-windows` и `net10.0`; оба таргета должны сохраняться.

## 3. Компоненты и поток запроса

Браузер панели → локальный обработчик моста → HTTPS серверного Cronopus →
прикладные операции Tasker → существующий SchedulerService и БД серверного узла.

Выделить общий сервис операций Tasker из затрагиваемых методов SchedulerHandler.
Локальные маршруты и новый API вызывают этот сервис с одинаковыми правилами проверки.
Не дублировать планировщик, правила payload, расписаний или запуска процессов.
Передача файлов и сетевые ожидания не должны удерживать блокировки планировщика.

Удалённый HTTPS-вход реализуется отдельным Kestrel-хостом внутри того же процесса.
Он позволяет обслуживать TLS без настройки сертификата через Windows HTTP.sys.
Добавление ASP.NET Core runtime необходимо учесть в self-contained публикации.
Вход выключен по умолчанию; сервер и клиент могут быть включены в одном экземпляре.
Новый порт по умолчанию — 38473, настраиваемый, независимо от панели и replay.
Если bind не удался, попробовать порт 0; показать фактический адрес и причину fallback.
Фактический порт публикуется в локальном статусе и данных подключения для оркестратора.
Существующие правила портов панели и replay в этой задаче не изменяются.

## 4. Доверие, авторизация и подключение

При первом включении создать постоянный node_id и самоподписанный TLS-сертификат.
Показывать IP-адрес, фактический порт, node_id, срок сертификата и SHA-256 отпечаток.
IP SAN сертификата формируется из настроенного адреса сервера.
Клиент доверяет только закреплённому сертификату и проверяет срок его действия.
Проверка отпечатка относится только к HTTP-клиенту этого подключения.
Глобальное отключение проверки TLS и принятие любого сертификата запрещены.
Обновление сертификата требует явного переноса нового отпечатка через доверенный канал.

На сервере создавать именованные ключи доступа из 32 криптографически случайных байт.
Секрет показывать один раз; хранить идентификатор, SHA-256 хеш, имя и признак отзыва.
Сравнивать хеши за постоянное время; любой запрос API требует Bearer-ключ.
Ключ даёт полное управление Tasker и файловые операции, описанные этой спецификацией.
Создание/отзыв ключей и изменение TLS доступны только в локальных настройках сервера.
Отзыв блокирует новые запросы, завершает наблюдение и отменяет незавершённые загрузки ключа.

В локальном Cronopus хранить имя подключения, HTTPS-адрес, node_id и отпечаток.
На Windows ключ и закрытый ключ сертификата защищать DPAPI CurrentUser и ACL.
В интерфейс отдавать только наличие сохранённого ключа; не возвращать его после сохранения.
Не включать секреты в URL, сообщения об ошибках, логи, экспорт подключений и публикацию.
Для net10.0 вне Windows: права файлов только владельцу; явно показывать этот режим хранения.
Настройки моста хранить на машине, вне общей БД задач и экспортируемого appsettings.

Первичное доверие: пользователь переносит адрес, отпечаток и ключ через существующий RDP.
«Проверить подключение» проверяет TLS, авторизацию, node_id, версию API и возможности.
При смене IP редактируется адрес; смена node_id или сертификата требует подтверждения доверия.
Раздел настроек показывает состояние listener и инструкцию открытия фактического TCP-порта.
Автоматическое изменение Windows Firewall и панели хостинга не входит в эту реализацию.
Удалённый вход не отдаёт wwwroot, терминал, replay, глобальную конфигурацию или другие API панели.

## 5. API и семантика операций

Все внешние маршруты находятся под `/bridge/v1`; ответы JSON, файлы — потоковые.
`GET /info`: node_id, версия API/приложения, capabilities, время/часовой пояс, лимиты.
`GET /tasks`: список с фильтрами, сортировкой и курсором; без payload и вывода.
`GET /tasks/{id}`: настройки, payload schema/values и версия редактируемой записи.
`POST /tasks`, `PUT /tasks/{id}`, `POST /tasks/{id}/clone`, `DELETE /tasks/{id}`:
создание, сохранение, клонирование и удаление через общий сервис Tasker.
`POST /tasks/{id}/actions/{action}`: run, stop, pause, resume, defer, enable,
disable, clear-queue, kill-instance и reset-successes.
Состав и аргументы действий проверяются по явному перечню, а не транслируются в произвольный URL.
`GET /tasks/{id}/instances` и `/queue`: порционные списки экземпляров и очереди.
`GET /tasks/{id}/output`: ограниченный вывод с курсором и фильтром экземпляра.
`GET /tasks/{id}/output/stream`: наблюдение только по явному включению пользователем.
`GET /changes?cursor=...`: ограниченные изменения состояния/счётчиков, включая удаления.
`GET /operations/{request_id}`: результат или состояние ранее принятой команды.

Отдельные явные операции предоставляют разбор параметров скрипта, предпросмотр запуска
и расписания, чтение/сохранение конфигурации проекта, build, ensure-venv и установку
зависимостей. Долгие операции возвращают operation_id; прогресс читается порционно.
Скрипты анализируются и зависимости устанавливаются на выбранном сервере.
Все поддерживаемые текущим Tasker исполнители используют имеющуюся серверную реализацию.
Открытие рабочего стола, редактора, папки ОС и интерактивного терминала на сервере
не входит в мост; соответствующие локальные кнопки в удалённом режиме заменяются
файловым просмотром там, где это применимо, либо скрываются.

Сохранять настройки, путь и payload согласованно через общую операцию сохранения.
Обновление/удаление требует версии записи (If-Match); конфликт возвращает 409.
Версия относится к редактируемой конфигурации, а не к изменяющимся счётчикам запусков.
Часовой пояс расписаний определяется сервером и показывается рядом с расписанием.
Пауза запрещает автоматические запуски; stop завершает выполнение по текущим правилам.
Resume сохраняет текущую семантику очистки паузы и отсрочки.

Каждая мутация получает уникальный request_id; сервер сохраняет его до выполнения
в локальном журнале операций, привязанном к node_id и ключу клиента.
Повтор с тем же ID и телом возвращает прежнее состояние; с другим телом — 409.
Завершённые операции хранятся 7 суток. Клиент не повторяет мутации автоматически.
Обрыв после отправки вызывает проверку /operations. После аварии сервера незавершённая
операция может получить outcome_unknown; автоматически выполнять её повторно нельзя.
Гарантия exactly-once через аварийное завершение процесса не заявляется.
Ошибки имеют code, message, request_id; коды HTTP: 400, 401, 403, 404, 409,
413, 429, 503. Несовместимая версия API блокирует подключение с понятным сообщением.

## 6. Серверные файлы и загрузка папок

`GET /files/roots` возвращает диски/корни, доступные серверному процессу.
`GET /files/list?path=...&cursor=...` возвращает порцию непосредственных потомков.
Пользователь может ввести абсолютный путь, подняться к родителю, создать каталог,
выбрать скрипт, просмотреть конфигурационный текст и загрузить файлы в выбранную папку.
Доступ к сетевому пути определяется учётной записью процесса; учётные данные RDP
не считаются автоматически доступными процессу. Ошибки прав показываются явно.
Произвольное удаление каталогов и удалённый файловый менеджер общего назначения не входят в объём.

Локальный выбор папки формирует манифест относительных путей и размеров, включая пустые папки.
Локальная панель передаёт файлы потоком; не кодировать файл целиком в JSON/base64.
Локальный backend пересылает данные ограниченными буферами; ключ остаётся на backend.
`POST /uploads` создаёт сессию назначения и возвращает конфликты и свободное место.
Число файлов по умолчанию ограничено 10000, манифест — 8 MiB, файл — 20 GiB;
лимиты настраиваются на сервере и возвращаются в /info.
Размер пакета ограничивается свободным местом и заданной сервером квотой временных загрузок.
Пользователь выбирает для конфликтов «пропустить» или явно подтверждает «заменить».
Относительный путь не может содержать выход из назначения, абсолютный корень,
alternate data stream или недопустимые для ОС имена; проверить коллизии регистра.
Ссылки и junction не обходятся рекурсивно при загрузке папки; показать пропущенные элементы.
Сервер проверяет каноническое назначение каждого файла и исключает выход через reparse points.

`PUT /uploads/{id}/files/{file_id}?offset=...` принимает блоки до 4 MiB;
`GET /uploads/{id}` возвращает принятые смещения, прогресс и ошибки.
Сессия привязана к ключу; после переподключения передача продолжается с подтверждённого смещения.
`POST /uploads/{id}/commit` проверяет размер/SHA-256, конфликты и публикует файлы.
`DELETE /uploads/{id}` отменяет передачу. Незавершённые сессии очищаются через 24 часа.
Временные файлы размещаются на томе назначения; замена каждого файла атомарная.
Папка целиком не считается атомарной: результат содержит статус каждого файла.
Изменение существующего файла после просмотра конфликтов требует нового подтверждения.
При блокировке файла старый файл сохраняется; показать ошибку и возможность повтора.
Загрузка не меняет автоматически путь задачи и не перезапускает работающие экземпляры.
Уже выполняющиеся скрипты могут читать дополнительные файлы: замена папки на лету
не гарантирует целостность их окружения. Для обновления рабочей задачи интерфейс
предлагает загрузить в новый каталог и затем явно сохранить новый путь задачи.

## 7. Интерфейс и переключение узла

В верхней части Tasker — компактный выбор узла и состояние соединения.
Подключения настраиваются в Config → Remote Tasker; серверный режим включается там же.
Использовать существующую тему и CSS tokens ui-themes; новый переключатель тем не нужен.
В формах, диалогах загрузки и подтверждениях показывать имя выбранного узла.
Все запросы Tasker идут через единый transport adapter: local или remote connection ID.
Локальный backend принимает только разрешённые операции моста, а не произвольный URL прокси.

Узел, task_id и поколение выбора образуют контекст каждого асинхронного действия.
При переключении отменять запросы/наблюдение, сбрасывать выбор и данные прошлого узла.
Запоздавшие ответы не могут обновлять новый экран; одинаковые task_id на разных узлах различаются.
Несохранённые изменения требуют выбора «сохранить / отбросить / остаться» до переключения.
Выполняющаяся загрузка остаётся привязана к исходному узлу; её прогресс содержит имя узла.
Недоступность сервера блокирует новые команды; не перенаправлять их на локальный Tasker.
Показывать время последнего успешного обновления; после подключения сверять состояние.
Сбой сети не очищает черновик и сохранённый ключ. Ошибка 401 требует исправить подключение.

## 8. Лимиты и поведение под нагрузкой

Списки: по умолчанию 100 элементов, максимум 500; серверная сортировка и фильтрация.
Изменения состояния: максимум 500 записей за запрос, опрос раз в 3 секунды,
один запрос за раз; в скрытом Tasker опрос останавливается.
Курсор ограниченного журнала изменений содержит эпоху запуска сервера;
после перезапуска или истечения курсора клиент получает требование перечитать список.
Не читать полный вывод и не опрашивать процессы каждого экземпляра при получении списка.
Опрос экземпляров и очереди выполняется только для открытой задачи и активной вкладки.

Логи: начальная порция до 200 строк/256 KiB; следующая страница имеет те же пределы.
Наблюдение: максимум один поток на подключение клиента, до 64 KiB/сек.
Фиксированная очередь потока — 256 KiB; при переполнении пропускать старые данные
и отправлять marker с количеством пропусков. Медленный клиент не тормозит писателя логов.
Курсор содержит эпоху и последовательность; устаревший курсор явно сообщает потерю данных.
В UI хранить максимум 2000 строк; не обещать историю, уже вытесненную серверным буфером.
HTTP-трафик выполняемых задач автоматически через мост не передаётся.

Передача: максимум 2 активных блока на подключение и 4 на сервер;
по умолчанию суммарно 8 MiB/сек на сервер, лимит настраивается.
API управления имеет отдельный лимит конкурентности 8 запросов на ключ;
при превышении отвечать 429 с Retry-After, не накапливать неограниченную очередь.
JSON тела до 8 MiB, обычный таймаут 15 секунд; долгие операции используют operation_id.
Все коллекции, очереди и журнал операций должны иметь лимит хранения и очистку.
В журнале аудита: ключ-ID, операция, task_id/путь, результат и длительность;
без содержимого payload, файлов, ключей и полного вывода. Ротация: 5 файлов по 10 MiB.

## 9. Проверки и критерии приёмки

1. Два независимых процесса Cronopus с разными БД и node_id: создание задачи на
   сервере, выбор серверного скрипта, сохранение настроек/payload и чтение после перезапуска.
2. Расписание, enable/disable, pause/resume/defer, ручной запуск с количеством,
   остановка экземпляра/задачи и очистка очереди сохраняют локальную семантику.
3. Клонирование, смена скрипта и From Script заменяют schema/values согласованно,
   сохраняя остальные изменения формы; запоздавший ответ другого узла игнорируется.
4. Без ключа, с неверным/отозванным ключом, неверным отпечатком и истёкшим
   сертификатом доступ запрещён; отзыв прекращает активную передачу и наблюдение.
5. Удалённые запросы к терминалу, Config, replay и другим маршрутам панели недоступны.
6. Потеря ответа после run не создаёт второй запуск; повтор request_id с другим
   телом отклоняется. После аварии неопределённый исход виден пользователю.
7. Два клиента одновременно редактируют задачу: второй видит конфликт версии,
   а не молча затирает настройки. Серверные счётчики не вызывают ложный конфликт.
8. Загрузка дерева с вложенными/пустыми папками, Unicode, пробелами и большим файлом;
   SHA-256 исходника и результата совпадает. Проверить отмену, продолжение и cleanup.
9. Конфликты, нехватка места, запрет записи, занятый файл, traversal, ссылки и
   изменение назначения между проверкой и commit не повреждают существующий файл.
10. Переключение узла во время запросов, одинаковые task_id, обрыв сети и
    недоступный сервер не приводят к командам/отображению данных другого узла.
11. Стенд: 1000 синтетических выполняющихся экземпляров и активные источники логов,
    одновременно загрузка файла и управление. Зафиксировать конфигурацию стенда,
    CPU/RAM, трафик, p95 задержки API и размер буферов за 15 минут.
    Цель: p95 простых запросов управления менее 1 секунды при RTT до 100 мс;
    лимиты передачи/буферов соблюдаются, память не растёт пропорционально объёму логов.
    Такой тест не считается доказательством запуска 1000 реальных внешних процессов.
12. Локальный Tasker проходит существующие регрессии; обе целевые сборки и
    self-contained публикация содержат зависимости HTTPS-хоста и не содержат секретов.
13. HTTPS и доступность по IP проверяются с другой машины. Проверка на localhost
    отдельно фиксируется и не заменяет доказательство прохождения firewall/сети.

## 10. Границы и следующий этап

Первая реализация включает весь описанный мост, файловую загрузку и ограниченные логи.
Её удобно выполнять по зависимым этапам: общий сервис Tasker; HTTPS/авторизация;
клиент и переключение; файлы; лимиты/наблюдение; интеграционная проверка.
Общий список узлов, relay, удалённый рабочий стол, интерактивный терминал,
автоматическая настройка firewall, синхронизация окружений и rolling deployment не включены.
Планировщик продолжает работу при потере клиента; отдельная Windows-служба не добавляется.
Поддержка сервера за NAT без доступного входящего порта требует отдельного решения.

После проверки этой спецификации пользователем подготовить отдельный план реализации
с перечнем файлов, миграций, проверок и порядком выполнения. Продуктовый код на
этапе этой спецификации не изменяется.
